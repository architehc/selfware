# Bounded Audit — Seven Agent Areas (read-only, evidence-based)

All seven areas were inspected by reading implementation bodies and their named test files. No source was edited. Findings are tied to `path:line`.

---

## 1. `src/agent/last_tool.rs` + `tests/unit/agent/last_tool/last_tool_test.rs`

**Retention & bounding.** The last tool result is stored per-agent on `Agent.last_tool_output` (not process-global), as a `LastToolOutput` struct carrying `tool_name`, `summary`, `full_output`, `success`, `exit_code`, `duration_ms` (`last_tool.rs:20-33`). `store_last_tool_output` (`last_tool.rs:39-53`) truncates two fields to fixed caps: `MAX_FULL_OUTPUT_LEN = 16_384` (`last_tool.rs:12`) and `MAX_SUMMARY_LEN = 512` (`last_tool.rs:15`). `retrieve_last_tool_output` returns a clone (`last_tool.rs:57-59`).

**Long Unicode.** Truncation uses `truncate_on_char_boundary` (`last_tool.rs:40-49`), which walks the byte index down until `is_char_boundary` holds, so a cut landing mid-codepoint cannot panic. The regression test `storing_long_multibyte_output_does_not_panic` (`last_tool_test.rs:52-72`) feeds 6000 `✿` (3-byte) chars and asserts the stored length is `≤ MAX_FULL_OUTPUT_LEN` and that `from_utf8` still succeeds — establishing the boundary-safe behavior. `storing_long_output_truncates` (`last_tool_test.rs:16-49`) pins the exact ASCII lengths (512 / 16384).

**Failed result.** The `success: bool` and `exit_code: Option<i32>` fields are stored verbatim; `default_last_tool_output` (`last_tool_test.rs:4-13`) confirms the default is `success=false`, `exit_code=None`. A failed result is retained with the same bounding rules — no special-casing.

**Limitation (supported).** Only the single most recent result is kept (one `Option<LastToolOutput>` slot); earlier results are overwritten. This is by design for `/last`, not a defect.

## 2. `src/agent/task_policy.rs` + `tests/unit/agent/task_policy/task_policy_test.rs`

**Read-only classification.** `task_is_read_only` (`task_policy.rs:69-113`) is deterministic and lexical. It sets `asks_for_report` from a fixed verb list (review/analyz/…/investigat, `task_policy.rs:78-91`) and `forbids_editing` from a prohibition list (`task_policy.rs:93-105`). For a prompt like *"Review the code in src/agent/ and report findings. Do NOT edit any files."* it returns `true` (test `review_prompt_classifies_read_only`, `task_policy_test.rs:13-21`).

**The inversion subtlety.** When `task_requires_mutation(ctx)` is true, the read-only verdict requires BOTH a report deliverable AND a *global* prohibition (`task_policy.rs:107-111`), via `global_no_edit_prohibition` (`task_policy.rs:120-151`) minus scoped exceptions handled by `prohibition_has_exception` (`task_policy.rs:163-176`). This is exactly what the tests pin: `scoped_no_edit_inside_implementation_task_stays_mutation` and `scoped_prohibition_with_report_word_does_not_flip_an_edit_task` (`task_policy_test.rs:33-77`) show "fix calculator.py, do not modify test_calculator.py, report the result" stays a mutation task, while `global_prohibition_with_report_deliverable_still_wins` (`task_policy_test.rs:79-92`) shows a global "do not edit anything" flips it read-only. The exception-clause case (e2e c40) is covered by `prohibition_with_exception_clause_does_not_make_a_task_read_only` (`task_policy_test.rs:23-31`).

**Constraints on mutations/completion.** The stored decision gates the guards: `read_only_classification_gates_requires_mutation_everywhere` (`task_policy_test.rs:94-124`) establishes that a review+meta task makes `current_task_requires_mutation()` false, disarming force-mutation and stagnation machinery. `plain_status_query_does_not_require_mutation` (`task_policy_test.rs:126-160`) establishes the three-class matrix: mutation task → requires mutation; review task → read-only + no mutation; plain query → NOT read-only-branded but still no mutation. The `[POLICY …]` envelope (`policy_envelope`, `task_policy.rs:235-252`) is tested for first-line placement and newline flattening (`task_policy_test.rs:162-189`).

**Limitation (supported).** Classification is purely keyword/substring based; a paraphrase that avoids every listed token (e.g. "give me the gist") would not be branded read-only. This is an acknowledged design choice, not a bug.

## 3. `src/agent/turn_artifacts.rs` + `tests/unit/agent/turn_artifacts/turn_artifacts_test.rs`

**Evidence per artifact.** `TurnArtifact` (`turn_artifacts.rs:39-77`) records: `step`, `timestamp`, sanitized `request_body`, raw `response_body`, `finish_reason`, `completion_tokens`, `prompt_tokens`, optional `reasoning_content`, `parsed_tool_calls`, an `AgentDecision` enum (`turn_artifacts.rs:22-36`: ExecutedTools/NoToolCall/NudgeInjected/Aborted/Completed/Refused), `elapsed_ms`, an optional `EvidenceSnapshot` ledger summary (`turn_artifacts.rs:81-107`), and `logprobs`.

**Filename scheme & restart.** `write_artifact` writes `turn_{step:04}.json` (`turn_artifacts.rs:245`), then `prune_old_artifacts` caps the directory at `MAX_TURN_ARTIFACTS = 500` by mtime (`turn_artifacts.rs:189-232`). The scheme is **step-indexed, not run-indexed**, so on a process restart the counter restarts and `turn_0001.json` is overwritten in place — the filename alone does NOT protect previous artifacts across restarts; only the 500-file mtime prune bounds growth. Tests confirm: `write_artifact_creates_file` (`turn_artifacts_test.rs:226-240`) asserts `turn_0001.json` exists and is valid JSON; `write_artifact_prunes_to_cap` (`turn_artifacts_test.rs:242-268`) writes 525 artifacts and asserts exactly 500 remain; `turn_artifact_roundtrips_through_json` (`turn_artifacts_test.rs:203-224`) pins field preservation including `evidence: None` compatibility.

**Sanitization.** `sanitize_request_body` walks the JSON tree replacing secret-named keys with `<redacted>` (`turn_artifacts.rs:135-176`); tests `sanitize_strips_top_level_api_key_and_authorization`, `sanitize_strips_nested_headers_with_mixed_case`, `sanitize_walks_deeply_nested_extra_body`, `sanitize_handles_arrays_and_prefix_variants`, `sanitize_preserves_token_count_fields`, `sanitize_redacts_token_suffix_keys` (`turn_artifacts_test.rs:65-201`) establish that `api_key`/`Authorization`/`*-token` are scrubbed while `prompt_tokens`/`completion_tokens`/`Content-Type` survive. `logprobs` preservation is tested at `turn_artifacts_test.rs:270-309`.

**Limitation (supported).** Capture is opt-in (`disable_turn_artifacts`, `turn_artifacts.rs:16`); with the default off, no per-turn evidence exists for post-mortem. The `.gitignore` helper is tested for idempotent non-clobbering (`turn_artifacts_test.rs:5-19`) and no-op-on-missing-dir (`turn_artifacts_test.rs:21-27`).

## 4. `src/agent/progress.rs` + `tests/unit/agent/progress/progress_test.rs`

**Signals distinguishing progress vs repetition/stagnation.** `ProgressEvent` (`progress.rs:26-83`) carries `StepStarted`, `LlmRequestSent`, `LlmResponseReceived`, `ToolCallStarted/Completed`, `GuardFired{kind,count}`, `StepCompleted{mutating_tools_so_far}`, subprocess events, `TaskCompleted/Failed`, and `TurnDecision{decision,detail}`. The progress-vs-stall distinction lives in two places: (a) `StepCompleted.mutating_tools_so_far` (`progress.rs:63-66`) counts real edits; (b) `GuardFired.count` (`progress.rs:56-60`) — a repeating guard shows an incrementing count rather than N identical lines, via `dedupe_consecutive` (`progress.rs:300-309`).

**Test coverage.** `simulated_loop_event_order` (`progress_test.rs:74-122`) pins the canonical 7-event ordering a `run_task` must honor. `simulated_loop_with_guard_fire` (`progress_test.rs:124-161`) establishes the guard fires strictly between `tool_call_completed` and `step_completed`. `dedupe_consecutive_suppresses_identical_lines_only` (`progress_test.rs:163-189`) proves: identical repeat suppressed, count-change printed, different line resets the window. `render_event_kv_covers_run_state_decisions` (`progress_test.rs:191-215`) pins the exact rendered shape of `budget_extension`/`context_trim`/`guard_fired` lines so headless output stays parseable. `render_turn_decision_kv`/`_no_detail` (`progress_test.rs:44-72`) confirm the `detail=` field is present only when non-empty. `multi_emitter_fans_out` (`progress_test.rs:29-42`) confirms `MultiProgressEmitter` forwards to all children.

**Limitation (supported).** `short_args_for` (`progress.rs:88-124`) only recognizes a fixed key set (path/file_path/file, command/cmd, pattern/query/search, url); a tool whose primary arg is named otherwise yields an empty `args_short` (`progress.rs:122`). The `StderrProgressEmitter` suppresses entirely when the TUI owns the terminal (`progress.rs:277-279`), so live stderr lines and TUI are mutually exclusive by design.

## 5. `src/agent/loop_control.rs` + `tests/unit/agent/loop_control/loop_control_test.rs`

**Repeated calls / failed tools / recovery.** `AgentLoop::next_state` (`loop_control.rs:245-266`) checks the cap BEFORE consuming a slot, so a refused slot is never counted — `cap_stop_never_reports_more_iterations_than_the_cap` (`loop_control_test.rs:78-108`) proves the summary reads `18/18`, never `19/18`. `productive_streak` (`loop_control.rs:135-192`) is the adaptive-budget evidence test: every window turn must have `had_success` and non-empty signatures, and a repeated `(name,args-hash)` is excused only if a *different* mutating call sits in the anchor→current span. Tests trace each branch: `productive_streak_extends_when_all_turns_productive` (`loop_control_test.rs:288-306`), `repeated_identical_call_is_not_progress` (`loop_control_test.rs:317-338`), `error_only_streak_is_not_progress` (`loop_control_test.rs:340-360`), `verification_rerun_after_each_mutation_earns_streak` (`loop_control_test.rs:410-427`), `same_mutation_reapplied_is_still_a_stall` (`loop_control_test.rs:449-466`), `adjacent_repeat_after_mutation_turn_still_breaks` (`loop_control_test.rs:481-497`), `alternating_two_probes_without_mutation_still_breaks` (`loop_control_test.rs:499-511`), and `shell_probe_repeat_is_fail_closed_without_args` (`loop_control_test.rs:513-535`) — the last shows `shell_exec` repeats never self-excuse because args are hashed (name-only mutation witness via `signature_is_mutating`, `loop_control.rs:126-128`).

**Budget extension & recovery decisions.** `extend_budget_once` (`loop_control.rs:196-206`) grants +25% of the ORIGINAL cap, max 4 grants (`MAX_GRANTS`, `loop_control.rs:33`); `extension_is_quarter_of_original_and_grants_up_to_four` (`loop_control_test.rs:364-381`) and `extension_lets_the_loop_run_past_the_original_cap` (`loop_control_test.rs:392-424`) trace the 8→10→12→14→16 ladder and the ceiling. `restore_budget_extension` (`loop_control.rs:224-227`) survives restart without shrinking below the configured cap or minting extra grants (`loop_control_test.rs:543-585`). `reset_budget_for_resume` (`loop_control.rs:257-268`) mirrors manual resume; `reset_budget_for_resume_mirrors_manual_resume` (`loop_control_test.rs:690-729`) confirms the chain counter is NOT reset.

**Branches that stop a task before a final answer.** (1) `next_state` → `Failed{MAX_ITERATIONS_STOP_REASON}` when the cap trips (`loop_control.rs:256-261`), the single source of truth matched by the autocontinue resume policy (`loop_control.rs:47-52`). (2) `productive_streak` returning false denies an extension, so the cap becomes terminal. (3) `MAX_AUTO_CONTINUES = 3` (`loop_control.rs:41`) turns a forever-progressing run into `AUTO_CONTINUE_LIMIT`. (4) Invalid transitions: `is_valid_transition` (`loop_control.rs:322-340`) rejects e.g. Planning→Completed, tested by `test_invalid_transition_rejected` (`loop_control_test.rs:192-200`). `approaching_limit_warning`/`_band` (`loop_control.rs:289-320`) inject 80%/90% wrap-up nudges; `test_approaching_limit_warning_at_80_pct`/`_90_pct`/`_zero_max` (`loop_control_test.rs:202-244`) pin them.

**Limitation (supported).** `productive_streak` requires a FULL window of evidence (`loop_control.rs:136-138`); a short history yields `false` even if every recorded turn was productive (`productive_streak_needs_full_window_of_evidence`, `loop_control_test.rs:308-315`).

## 6. `src/agent/failure_mode.rs` + `tests/unit/agent/failure_mode/failure_mode_test.rs`

**Selection.** `FailureMode::classify` (`failure_mode.rs:118-330`) is purely observational over agent counters. For `RunOutcome::NaturalCompletion` (`failure_mode.rs:143-232`) it walks: FakeComplete (0 mutations + final-answer marker + not read-only, `failure_mode.rs:148-160`), FakeComplete via `current_task_requires_mutation` (`failure_mode.rs:167-178`), NoChange (`failure_mode.rs:185-195`), then REAL_EDIT only when `written_paths()` non-empty OR `shell_write_evidence()` (`failure_mode.rs:203-232`), else `RequiredEditMissing` for mutation tasks. The whole natural-completion verdict is then folded with `with_verification_verdict` (`failure_mode.rs:234`, `failure_mode.rs:470-516`). For `Failed{reason}` it matches explicit markers in priority order: PrefillBreaker → FAKE_COMPLETE_LOOP → NONTERM_PROSE_NO_TOOL → READ_LOOP_NO_EDIT → PermissionRequired → safety-blocked → MaxIterations → BudgetExhausted → Timeout → SelfwareError → counter fallback (`failure_mode.rs:236-322`).

**Classifications affecting recovery.** `is_nonfailure` (`failure_mode.rs:106-110`) = {Success, NoChange} drives the ✅/❌ banner and the `TaskCompleted` vs `TaskFailed` event split; `failure_verdict_as_error` turns a non-nonfailure into non-zero exit (tested in `c40_mutation_task_with_zero_mutations_is_a_typed_failure`, `failure_mode_test.rs:690-716`). `RequiredEditMissing` is explicitly a failure twin of `NoChange` (`failure_mode.rs:80-88`).

**Edge cases checked by real tests.** `classify_probe_only_mutations_label_no_change_not_real_edit` (`failure_mode_test.rs:63-83`) — shell-probe "mutations" with no disk write → NoChange. `classify_shell_redirect_write_counts_as_real_edit` (`failure_mode_test.rs:85-104`) — `printf 'x' > out.txt` earns REAL_EDIT. `classify_read_only_task_with_final_answer_is_no_change_not_fake_complete` vs `classify_mutation_task_with_final_answer_stays_fake_complete` (`failure_mode_test.rs:118-152`) pin the read-only exemption. `classify_permission_required_instead_of_max_iterations` (`failure_mode_test.rs:186-232`) is a strong edge case: a 3-iteration confirmation stop must not be filed as MAX_ITERATIONS and its advice must not say "raise max_iterations". `scattered_safety_blocks_do_not_relabel_a_real_timeout` (`failure_mode_test.rs:300-326`) shows the dominance rule `blocked>=2 && blocked*2>=window` (`failure_mode.rs:438-442`). `truncate_splits_at_char_boundaries` (`failure_mode_test.rs:470-483`) covers the `αβγδ` mid-codepoint case. `max_iter_failure_read_only_skips_fake_complete` (`failure_mode_test.rs:154-162`) directly exercises `classify_max_iter_failure`.

**Limitation (supported).** `FailureKind::Unknown` (`failure_mode.rs:99`) is defined but never produced by `classify` — every path returns a concrete kind, so `Unknown` is effectively dead in the classifier (only reachable if a caller constructs it). The `truncate` helper counts *chars* via `char_indices().nth(max)` (`failure_mode.rs:560-566`), so `max` is a char count, not bytes — consistent with the test.

## 7. `src/agent/verification_scope.rs` + `src/agent/verification.rs`

**Check identity.** `check_id_for` (`verification_scope.rs:965-1043`) normalizes a command to the check it performs. Cargo invocations are parsed into a `CargoCheckShape` (`verification_scope.rs:742-758`) with `sub`/`scope`/`narrowing`/`filters`, then `render()`ed canonically (`verification_scope.rs:850-884`). Non-cargo commands drop non-subset flags but keep `SUBSET_BOOL_FLAGS` (`verification_scope.rs:700-712`). Tested by `check_id_preserves_test_selectors_and_drops_flags` (`verification_scope.rs:1046-1078`) and `check_id_keeps_every_subset_selector_and_strips_redirections` (`verification_scope.rs:1080-1110`), which pin `cargo test --lib 2>&1` → `cargo test --lib`, `cargo test --lib -- --nocapture` → `cargo test --lib`, `-p core` → `--package=core`, and `cd sub && cargo test --lib` → `cargo test --lib`.

**Scope.** `VerificationScope::relevance_to` (`verification_scope.rs:63-84`) returns InScope when the project root equals or is under the task root, OutOfScope only when it strictly encloses it, NoRunner when `runner_exists==Some(false)`, else Unknown. `blocks_completion` (`verification_scope.rs:100-110`) is fail-closed: only a relevant, non-stale, non-{OutOfScope,NoRunner} failure blocks. `clears` (`verification_scope.rs:126-150`) requires same scope AND either identical `check_id` or a structural `covers` relation (`verification_scope.rs:905-940`). Tests: `cargo_resolves_the_enclosing_manifest_not_the_working_directory`, `python_passes_and_an_unrelated_parent_rust_build_fails`, `a_relevant_failing_test_blocks_completion`, `an_unrelated_green_check_does_not_erase_a_relevant_failure`, `a_result_taken_before_the_latest_edit_is_stale`, `a_task_that_includes_both_projects_keeps_both_checks`, `an_unestablished_scope_still_blocks`, `a_pass_clears_its_own_failure_even_when_no_project_can_be_resolved`, `a_sibling_project_is_not_silently_dismissed`, `missing_cargo_manifest_is_no_runner_not_a_failure`, `python_unittest_failure_still_blocks_and_a_pass_discharges_it`, `passing_test_subset_cannot_clear_failing_full_suite`, `subset_selecting_passes_cannot_clear_broader_failures`, `ledger_keeps_full_suite_failure_after_lib_only_pass` (`verification_scope.rs:1046-1158`).

**Zero-tests case (from actual bodies).** `runner_output_proves_no_tests_ran` (`helpers.rs:1929-1972`) first checks a structured `no_tests_ran:true`, then vetoes on any failure marker, then declares "nothing ran" when no positive tally exists AND a zero-shaped marker is present (`running 0 tests` with all `0 passed`, pytest `no tests ran`/`N deselected`, `Ran 0 tests`, go `[no test files]`/`[no tests to run]`, jest `No tests found`, mocha `0 passing`, TAP `# tests 0`). `annotate_zero_test_verification` (`helpers.rs:1992-2028`) then rewrites the result to `success:false, no_tests_ran:true` with an honest message, but only for test-executing calls (`verification_call_ran_no_tests`, `helpers.rs:1975-1990`) — a compile check legitimately runs no tests and keeps its credit. Tests: `zero_test_runner_output_is_recognised_across_runners`, `runs_that_executed_tests_are_not_zero_test_runs`, `libtest_summary_alone_is_not_success_credit`, `a_structured_cargo_test_result_with_no_tests_ran_is_recognised`, `only_test_executing_calls_are_zero_test_runs` (`tool_dispatch_test.rs:6234-6360`).

**Shell-redirection case (from actual bodies).** `shell_command_is_masked_verification` (`helpers.rs:1480-1499`) flags a runner whose exit status is masked by a pipe/`;`/`||` (e.g. `cargo test | grep …`, `cargo test; true`), but NOT `cargo test 2>&1` (descriptor dup keeps status authoritative) nor info-only/no-op runs. `strip_output_redirections` (`helpers.rs:2085-2103`) drops `>`,`>>`,`2>`,`&>` and their targets while keeping `2>&1`. `masked_run_uncredited_reason` (`helpers.rs:2031-2053`) distinguishes three gaps: filtered/redirected output (never earns credit), truncated/paginated output, and complete-but-ambiguous output. `unmasked_test_runner_command` (`helpers.rs:2055-2083`) reconstructs the authoritative rerun form, preserving a leading `cd DIR &&` prefix. Tests: `masked_verification_runner_detection`, `filtered_runner_output_does_not_reach_result_unfiltered`, `redirected_then_filtered_runner_output_earns_no_credit`, `incomplete_tool_output_earns_no_masked_success_credit` (`tool_dispatch_test.rs:5666-5935`). In `verification.rs`, `recent_uncredited_masked_run` (`verification.rs:1361-1395`) and `uncredited_masked_run_note` (`verification.rs:1397-1414`) surface these in gate rejections, and `fresh_authoritative_pass` (`verification.rs:1948-2027`) requires an UNMASKED, in-scope, exit-0 pass at the credited revision (`logged_exit_status_is_zero`, `verification.rs:2044-2056`).

**Limitation (supported).** `verification.rs` has no separate named test file in the focus list; its tests live at `tests/unit/agent/verification/verification_test.rs` (`verification.rs:3900-3901`), which was not among the seven required files — the zero-test/redirection logic is instead exercised through `tool_dispatch_test.rs` and the in-module `#[cfg(test)]` block of `verification_scope.rs`. `same_scope_as` (`verification_scope.rs:153-166`) treats two unresolvable roots as equal only via the working-directory fallback, so two different unknown-root commands in the same cwd clear each other but not across cwds.

## Confirmed findings by severity

- **P3 (informational, by-design):** `last_tool.rs` keeps exactly one result slot; `task_policy.rs` classification is lexical; `progress.rs` `short_args_for` recognizes a fixed key set; `failure_mode.rs` `Unknown` variant is unreachable from `classify`. None are defects — each is a documented, tested design choice.
- **P3 (documentation gap):** Area 7's `verification.rs` tests are in a file outside the seven named ones; the required behavior is nonetheless fully covered by `verification_scope.rs`'s in-module tests and `tool_dispatch_test.rs`. No uncovered logic found.
- **No P1/P2 defects confirmed.** All seven areas' behaviors match their test expectations; the char-boundary truncation, the scoped-vs-global prohibition split, the step-indexed artifact overwrite, the pre-consume cap check, the productive-streak mutation-witness rule, the failure-classifier priority order, and the masked/zero-test verification rules are each backed by at least one real test.
